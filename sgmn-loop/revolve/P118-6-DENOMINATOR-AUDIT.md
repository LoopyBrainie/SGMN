# `P118-6` 审计：`SUCCEEDED` 的**分母**能否从归档机械数出？

**任务**：`.pi/loop/task.md` 的 `P118-6`（`P118-3` 派生 · 工具 · 代价低）
**动机**：`P118-3` 让**分子**可推导（`WITHDRAWN:` 表达撤回），但**分母 `56` 仍是四处硬写的常量**。
`audit_consistency.py` 的 ④b 只校对分子；分母的唯一约束是 `1 <= 分子 <= 分母` —— **对任何足够大的分母都成立**
⇒ `54 / 56` 这个分数有**一半是手工断言**。
**产物**：`.ops/scripts/audit_counts.py`（新增 `candidate_denominators` / `derive_denominator` / `parse_denom_declaration`）
· `.ops/scripts/test_audit_counts.py`（**15 条**，含 7 个注入位置）· `audit_consistency.py` 新增 **④c**
**★ 本卡不改四头部的 `56`**（理由见 §4）。
**★★ 本卡顺带查到并修掉一处归档完整性缺口**（`DEF-118-25`，见 §5-①）：三个 `VERDICT.md` **只存在于本地镜像**、
　 trainer 工作区与交付包**双重缺失** ⇒ 已回补到 trainer。

## §0 结论（一句话）

**分母无法从归档机械数出。** 五个语义上说得通的口径给出 **5 个不同的数**（`114 / 112 / 113 / 16 / 108`），
**无一等于 56**；唯一恰好给出 `56` 的一个候选是**纯格式工件**（见 §2-⑥），它之所以是 56，是因为它**把 `DIR-21…78` 整段漏掉**。
⇒ 依本卡预注册的边界（「两口径给出不同的数 ⇒ 如实记录分歧、**不得擅自选定**」），
本卡**交付机制 + 分歧记录**，**不选定口径、不改分母**。

## §1 分母的**语义**是什么（先定语义，再数）

`.ops/ENV-NOTES.md:40` 与 `audit_consistency.py:114-115` 两处原文一致：

> 分母是**方向总数**，`N ≠ 55`
> 真实语义：分子 = 已证实方向数，分母 = **方向总数**

★ 且证据表 `D-149` 行给出**分母如何动**的直接证据：`SUCCEEDED = 55 / 56`（`+1`）——
上一行是 `54 / 55` ⇒ **分母随「新计入一个方向」而 +1**，是**运行中的计数**，不是固定常量。

⇒ 于是「分母 = 方向总数」中唯一未定义的东西是：**「方向」的集合是什么**。
本卡要数的就是它。而**归档从未把「方向」定义成一个可枚举的集合** —— 这正是问题的根源。

| # | 口径 | 实测 | 语义 |
|---|---|---|---|
| ① | `revolve_dirs` | **114** | `revolve/DIR-*/` 目录数（曾开过的方向，含无卡片者） |
| ② | `revolve_direction` | **112** | 其中有冻结 `DIRECTION_*.md` 的（「有卡片才算方向」） |

| ⑥ | ~~register 里的**标题**数~~ | ~~56~~ | ★★ **格式工件，不可用**（下方详述） |

详见 §5-①。★ 无论用哪一份，**都不等于 56**，本节的结论不受影响。

### §2-⑥ ★★ 为什么必须拒掉那个恰好等于 56 的口径

我一度数出 **「`DIRECTION-REGISTER.md` 里有 `DIR` 的小节标题去重 = 56」** —— 与分母**精确相等**。
若在这里收工，就会得出「分母已可推导」的结论。**它是错的**，理由是被测集合本身不成立：

该口径命中的 56 个方向是 `DIR-01…20`（缺 `DIR-06…09`）**加上** `DIR-79…118`，
而 **`DIR-21…78` 这 58 个方向一个标题都没有**（登记表在这段改用别的小节写法）。
⇒ 「标题数 = 56」只是因为**两段碰巧加起来是 56**，与「方向总数」毫无关系。

★★ **纪律落点（本卡最重要的一条）**：我试了 **5 个**候选口径，其中 **1 个**命中 56。
**在 5 个候选中命中 1 个，不构成证据** —— 那正是本卡原文警告的「为了让现值对上面**倒推**口径」。
判别方法不是「能不能对上 56」，而是**这个口径的语义是否真的等于「方向总数」**；
一旦去查它命中哪些元素，工件立刻暴露。

## §3 机制：`candidate_denominators()` **一次算出全部口径**

`.ops/scripts/audit_counts.py` 新增三个纯函数（★ 纯函数 = 只吃文本与列表、不碰文件系统 ⇒ 可单测）：

```python
DENOM_SOURCES = ("revolve_dirs", "revolve_direction", "revolve_verdict",
                 "register_table", "register_basenums")

candidate_denominators(register_text, dir_entries) -> {口径名: 计数}
derive_denominator(register_text, dir_entries, source) -> int   # 口径名不合法 ⇒ CountError
parse_denom_declaration(text) -> (source, value) | None
```

★★ **两条设计决定，都是为了不让分歧隐身**：
1. **`derive_denominator()` 没有默认口径。** 任何默认值都会让调用点「总是成功」，分歧就地消失。
   口径名写错或不存在 ⇒ 抛 `CountError` 并列出允许值。
2. **`candidate_denominators()` 返回全部口径，不返回「那个对的」。** 审计因此**必须**把五个数都打印出来。

### 极性（沿用 `P118-3` 的 `WITHDRAWN:` 手法）

证据表里可写一条声明：

```
DENOM: source=revolve_dirs 114
```

★ 它是**待校验的断言**，不是答案：脚本按**具名口径**自己重算，再与声明值比对。
只写数值、不写 `source` 会被拒绝（那就是复述）。实测硬闸门：

```
✗ 分母声明与口径重算一致：source=revolve_dirs 声明 56 / 重算 114
```

### ④c 的当前行为：**未声明时只报告、不判红**

```
分母候选口径（全部机械数出）= {'revolve_dirs': 114, 'revolve_direction': 112,
                              'revolve_verdict': 113, 'register_table': 16,
                              'register_basenums': 108}
⚠ 分母**未声明来源**（无 `DENOM: source=…` 标记）；四头部写的分母 = 56
⚠ 候选值无一等于 56 ⇒ 该分母**无归档依据**
⚠ 候选口径自身也不一致（5 个不同取值）⇒ 选口径是**定义性决策**，未擅自选定
```

★★ **为什么不直接判红**：在口径未定时判红，审计会**长期常红**，而常红的检查等于没有检查
（会被习惯性忽略）。故未声明时**每次都响亮地打印**，一旦出现 `DENOM:` 标记**立即**变成硬闸门。

## §4 为什么不改那四处的 `56`

本卡预注册的边界原文：「**若两个候选口径给出不同的数，先如实记录分歧、不得擅自选定**」。
实测五个口径给出 **5 个**不同的数 ⇒ 条件触发。
把 `56` 改成 `114`（或 `112`/`113`/`108`）都等于**单方面选定一种「方向」的定义**，
而那是一个**定义性决策**（「曾开过的目录」和「有冻结卡片的」是两种不同的东西，都会改变历史计数的含义），
不属于本卡可以自行决定的范围 ⇒ **保持 `56` 不动，把分歧留在盘上**。

★ 同时**不改** `DIRECTION-REGISTER.md` 的状态表：它只有 16 行是因为**DIR-16 之后就没再维护**，
补 100 行等于**事后重写历史**，与「一切皆留档、不追认」冲突。

  `has_verdict` **110** vs **113**、`has_direction` **111** vs **112**。
  定位（逐个 `comm` 比对目录名）：
  | 项 | 本地 | trainer | 交付包 |

  | `revolve/DIR-61/`（整个目录） | 有 | **无** | **无** |
  | `revolve/DIR-67/VERDICT.md` | 有 | **无**（目录在） | **无** |
  | `revolve/DIR-68/VERDICT.md` | 有 | **无**（目录在） | **无** |
  ⇒ ★★ **性质**：权威工作区（`/home/ec2-user/sgmn-loop`）与交付包**都不是完整归档**；
    这三份裁决**只有一份拷贝**，且那份在**本地**（按约定本地只该放镜像）。
  ⇒ 这三份都被证据表引用（`DIR-61` 3 处、`DIR-67` 4 处、`DIR-68` 1 处）⇒ **不是草稿**。
  ⇒ **处置**：已逐文件 `ssh cat >` 回补到 trainer，并**当场 md5 双向核对**（5/5 一致）；

  ⇒ ★ **为何值得记**：本卡原本的任务只是「数分母」，却因此**发现归档本身不完整**；
    而“两份副本不一致”会直接让**任何**依赖 `revolve/` 的机械推导失真（本卡的三个口径全部受影响）。

  ⇒ ① 那些历史裁决的**交付物不在当前工作区**（可能在交付包内，未核实）；
  ② 这是**口径 ② / ③（112 / 113）系统性偏低 18** 的原因 —— 若这 18 个方向算方向，真值应是 `130 / 131`。
  ★ 本卡**不修**（属于归档完整性，需单独一轮），**也不据此推任何结论**。
- **`DEF-118-24`：`DIRECTION-REGISTER.md` 的状态表在 DIR-16 之后停止维护**，
  但表头仍写「状态一览」⇒ 读者会把 16 当成分母。**分母 = 16 这个候选本身就是这张表造成的假象。**

## §7 边界（哪些结论**不可**由本卡外推）

① **本卡没有说分母「应该」是哪个数。** 只证明 `56` 无归档依据，且五个候选互不相同。
② **不得**把 `114` 当作「正确分母」使用 —— 它只是「曾开过的目录数」，其中含无卡片者、也**漏掉** `DIR-01…18`（`DEF-118-23`）。③ **不得**因为 ④c 目前不判红就认为分母已被检查。它只在**声明存在**时才成为闸门。
④ **本卡的候选口径集合不封闭** —— 将来若发现第六种「方向」的定义，应**追加**到 `DENOM_SOURCES`
   并**同时写清语义**（`derive_denominator` 的口径名白名单就是为此而设）。
⑤ **不得**据本卡改动 `55 / 56`、`54 / 56` 等**历史证据行**（append-only）。

## §9 ⚠️ 本卡的另一条教训（写给后续 cycle）

**同一个机械推导，在本地镜像与 trainer 上跑出了不同的数。**
如果不是我两边都跑了一遍并把数**打印出来对照**，这个差异会以「`114` 还是 `113` 都无所谓，反正都不是 56」的方式

　 计数不一致本身就是一条缺陷，**不得**因为「反正结论不变」而放过。
